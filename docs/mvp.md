# Scootly — MVP (этап 2, подготовка к разработке)

Определение минимального продукта первой версии: что **обязательно** работает на релизе,
что сознательно отложено. Документы-спутники: [DB](./db/schema-mvp.md), [API](./api/openapi.yaml),
[WebSocket](./api/websocket.md).

## 1. Цель MVP

Пользователь Telegram Mini App проходит **полный платящий цикл без ручного вмешательства**:

```
вход через Telegram → видит самокаты на карте → бронирует → едет → платит (холд → capture)
```

Всё остальное — рост после MVP.

## 2. Обязательно должно работать (in scope)

### Этап 1 — платящий цикл (фичи 1–8) ✅

| # | Фича | Минимальная реализация | Ссылки |
|---|------|------------------------|--------|
| 1 | **Авторизация** ✅ | Вход через Telegram `init-data` (Mini App) → JWT (access + refresh). Телефон — опционален | ADR-0007, ADR-0013 |
| 2 | **Карта + самокаты рядом** ✅ | `GET /scooters/nearby` (Redis GEO-кэш, свежесть по SLO) + live-обновления статуса по WS | ADR-0011 |
| 3 | **Бронирование** ✅ | Бесплатная бронь на 10 мин, TTL-автоснятие, отмена вручную. Без race: `UPDATE ... WHERE status='available' RETURNING` | ADR-0003, ADR-0015, §5.1 (тесты) |
| 4 | **Поездка** ✅ | Старт из брони или напрямую (unlock самоката), тик стоимости в UI, финиш (лок + расчёт) | ADR-0016 |
| 5 | **Оплата** ✅ | YooKassa: привязка карты, **холд на старте → capture на финише**, идемпотентность `ride:{rental_id}` | ADR-0003, ADR-0014 |
| 6 | **Компенсация unlock-fail** ✅ | Замок не подтвердил unlock за 10 c → холд снят, юзер уведомлён, самокат в `offline` | ADR-0006 |
| 7 | **История** ✅ | Список поездок и платежей пользователя | — |
| 8 | **Доменные события** ✅ | Outbox → Kafka (`rental.*`, `payment.*`, `scooter.status-changed`), WS-фан-аут в приложение | ADR-0008, `asyncapi.yaml` |

### Этап 2 — интеграции и приёмка (после фич 1–8)

Этап 1 закрыт на эмуляторах (замки, эквайринг) и локальном стеке. Этап 2 доводит
контур до приёмки (§5) без расширения скоупа продукта — §3 остаётся out of scope.

| # | Задача | Минимальная реализация | Ссылки |
|---|--------|------------------------|--------|
| 9 | **Метрики → Grafana** ✅ | `metrics-exporter-prometheus` (`:9000`) во всех сервисах со счётчиками; дашборды Grafana: `rides_started_total`, `unlock_failed_total`, `battery_low_total` | §5, `infra/monitoring` |
| 10 | **Реальные замки (MQTT)** ✅ | `Locks::Emulated` → MQTT-шлюз: команды unlock/lock, ack за 10 c, дедуп `msg_id` в Redis | ADR-0002, ADR-0006, ADR-0009 |
| 11 | **YooKassa в staging** | Реальные ключи эквайринга, вебхук `payment.succeeded/canceled`, сверка с YooKassa раз в 5 мин | ADR-0003, ADR-0014, openapi `paymentWebhook` |
| 12 | **Сервисы в docker-compose** | Все сервисы + `outbox-relay` в compose с healthcheck-зависимостями: `make up` поднимает полный стек | `docker-compose.yml` |
| 13 | **DoD-прогон на staging** | Полный цикл (1)–(6) e2e без ручных правок в БД; k6 `p95 unlock < 2 c`; отметка чекбоксов §5 и §5.1 | §5, `tests/load/rental-unlock.js` |

Тариф MVP: один — **per_minute** (разблокировка фикс + цена минуты, значения в конфиге/env).
Деньги — только в копейках (`INT`), никогда во float.

## 3. Сознательно НЕ делаем (out of scope)

- Подписки, пакеты минут, промокоды, рефералка
- Операторское RN-приложение, тикеты поддержки, задачи операторов (ADR-0004/0012 — позже)
- Зоны (разрешённые/запрещённые), парковки, штрафы
- Телеметрия IoT-стримом, замена батарей, shift-менеджмент
- Push/FCM — уведомления только внутри Mini App / Telegram-ботом
- Оплата СБП, Apple/Google Pay, наличные
- Админ-панель — самокаты заводятся сидером (`backend/tools/seeder`)

## 4. User stories (критерий «готово»)

1. Как юзер, я открываю Mini App и сразу вижу самокаты рядом — без регистрации по forms.
2. Как юзер, я бронирую самокат и вижу обратный отсчёт; по истечении TTL бронь снимается автоматически.
3. Как юзер, я жму «Начать поездку» — самокат разблокируется, холд виден в моём банке.
4. Как юзер, я завершаю поездку — замок закрывается, деньги списываются, я вижу чек (время, минуты, сумма).
5. Как юзер, у которого самокат не разблокировался, — я НЕ плачу и получаю уведомление.
6. Как юзер, я вижу историю своих поездок и платежей.

## 5. Критерии приёмки (Definition of Done)

- [ ] Полный цикл (1)–(6) проходит в staging end-to-end без ручных правок в БД.
- [ ] Двойная бронь одного самоката невозможна (race-тест: 2 параллельных запроса → 1×201, 1×409).
- [ ] Unlock-fail за 10 c → `payments.status = canceled`, холд снят (ADR-0006).
- [ ] Повторные `finish` / вебхук YooKassa не дают двойного списания (`UNIQUE idempotency_key`).
- [ ] `p95` unlock < 2 c — `k6 run tests/load/rental-unlock.js`.
- [ ] PG — source of truth для брони/поездки; Redis только TTL-триггер + GEO-кэш (ADR-0003).
- [ ] Бизнес-метрики в Grafana: `rides_started_total`, `unlock_failed_total`, `battery_low_total`.

### 5.1. Бронирование (#3): тестовый контракт

Фича считается готовой, когда зелёные все кейсы (контракт `POST /reservations`,
`DELETE /reservations/{id}` — в `docs/api/openapi.yaml`):

- [ ] **Race:** 2 параллельных `POST /reservations` на один самокат → 1×201, 1×409
      (`UPDATE ... WHERE status='available' RETURNING` + `uq_active_booking_per_scooter`).
- [ ] **TTL:** бронь с истекшим `expires_at` → `expired`, самокат снова `available`
      (Redis-триггер автоснятия + фоновый джоб сверки с PG).
- [ ] **Повторный запрос:** повторный `POST` на тот же самокат до истечения TTL
      не плодит дублей — та же бронь / `409 reservation_active_exists`
      (`Idempotency-Key` для броней в контракте нет: идемпотентность — через активную
      бронь; ключи `hold:`/`ride:` относятся к платежам, ADR-0014).
- [ ] **Redis недоступен:** бронь создаётся (PG — source of truth → 201),
      TTL-триггер догоняет джоб сверки (ADR-0003).
- [ ] **Rollback транзакции:** бронь + запись outbox пишутся атомарно — сбой
      оставляет самокат `available`, ни брони, ни outbox-записи нет.
- [ ] **Рестарт сервиса:** активная бронь переживает рестарт rental-service
      (состояние восстанавливается только из PG).
- [ ] **Лимит:** у юзера уже есть активная бронь → `409 reservation_active_exists`
      (частичный UNIQUE: не больше одной активной брони на юзера).

## 6. Верхнеуровневые риски MVP

| Риск | Митигация |
|------|-----------|
| Двойное списание / потеря холда | Идемпотентные ключи `hold:`/`ride:` + сверка с YooKassa раз в 5 мин (ADR-0014) |
| Race на бронь | `UPDATE..WHERE..RETURNING` + partial UNIQUE (ADR-0003) |
| Телеметрия/PII в логах | Маскирование через `common::telemetry` (CI ловит сырой `phone`) |
| Рассинхрон Redis-TTL и PG | Фоновый джоб сверки (ADR-0003) |
