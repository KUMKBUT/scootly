# 0010. DLQ-топология для Kafka-консюмеров

- Status: accepted
- Date: 2026-09-29
- Deciders: scootly team

## Context

Консюмеры (scooter, operator, support, notification, payment-reconciliation) могут
падать на «ядовитых» сообщениях: битый payload, несовместимая версия, временная
ошибка внизstream. Без политики сообщение либо блокирует партицию, либо теряется молча.

## Decision

1. Для каждого consumer-топика — парный DLQ: **`<topic>.v1.dlq`**
   (например `rental.events.v1.dlq`).
2. Политика ретраев: **3 попытки с экспоненциальным backoff (1s / 5s / 25s)**,
   после — сообщение целиком (payload + заголовки + причина + stack) в DLQ.
3. Ретраи — in-process (таймер консюмера), без отдельных retry-топиков: интервалы
   короткие, отдельная топик-механика не оправдана.
4. **Разбор DLQ — ручной** (джоб/скрипт), глубина DLQ — метрика с алертом
   Grafana → Telegram при > 0 на протяжении 10 мин.
5. Контракты DLQ — в `docs/api/asyncapi.yaml` (секция `x-kafka-dlq`).

## Consequences

- Плюсы: ни одно сообщение не теряется и не блокирует партицию; отладка по
  сохранённому оригиналу сообщения.
- Минусы: ручной разбор (приемлемо для пет-проекта); нужен дашборд глубины DLQ.
