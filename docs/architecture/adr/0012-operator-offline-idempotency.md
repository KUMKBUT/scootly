# 0012. Идемпотентность офлайн-операций оператора (client_op_id)

- Status: accepted
- Date: 2026-09-29
- Deciders: scootly team

## Context

Operator App — offline-first (ADR-0004): SQLite-очередь + Sync Engine с ретраями.
Ретраи и повторная отправка после смены устройства/очистки очереди могут создать
дубли: две задачи «замена АКБ», два закрытых shift.closed, две копии фото.

## Decision

1. **Каждая офлайн-операция несёт `client_op_id` (UUIDv4)** — генерирует RN один
   раз в момент создания операции и хранит в SQLite до успешного ack.
2. Бэкенд: **`UNIQUE(client_op_id)`** на офлайн-сущностях (начиная с
   `operator_tasks.client_op_id`). Повтор → существующая запись / идемпотентный
   ответ, дубль не создаётся.
3. Presigned URL для фото в MinIO — **TTL 24 часа**: хватает на длинный офлайн,
   окно утечки ссылки ограничено.
4. Конфликты статусов (например, задача уже completed другим оператором) решаются
   проверкой статуса на сервере: операция с `client_op_id` отклоняется с
   объяснением, Sync Engine помечает её «conflict» в очереди.

## Consequences

- Плюсы: exactly-once эффект на бэке при at-least-once доставке; очередь RN
  можно чистить только после 2xx.
- Минусы: колонка и проверка в каждой офлайн-ручке; UI обязан показывать
  конфликт (редкий случай).
